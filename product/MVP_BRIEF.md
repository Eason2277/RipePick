## 1. 文档目的

本文档用于定义 RipePick 第一版产品需要验证的核心价值、目标用户、核心使用场景和功能边界。

它是 MVP 阶段的范围基线，不替代后续的详细 PRD、交互设计、UI 设计、技术设计和测试方案。

## 2. 产品定位

RipePick 是一款以水果为核心的个人健康饮食决策助手。

它帮助经常吃水果、关注健康饮食的人，根据当前饮食状态、时间、季节和个人目标，获得具体的水果选择与早餐搭配建议。

RipePick 不是购物平台，也不提供医疗诊断或治疗建议。

## 3. 产品目标

帮助用户把模糊的健康饮食目标转化为清晰、可执行的水果和早餐方案，同时通过简明解释提升用户的健康饮食认知。

## 4. 目标用户

### 4.1 MVP 主要用户

每天或经常主动吃水果、关注健康饮食、但在具体饮食场景下不确定如何选择的年轻成年人。

### 4.2 用户特征

- 有稳定的水果消费或食用习惯
- 愿意根据自身状态调整饮食
- 关注季节、营养和搭配
- 需要快速、易理解、可执行的建议
- 不一定具备系统的营养学知识

### 4.3 暂不作为主要用户的人群

- 需要医疗级营养治疗方案的人群
- 需要精确运动营养处方的专业运动员
- 只关注价格和购买渠道的用户

## 5. 用户核心问题

用户知道水果与健康饮食有关，但在具体场景下不知道：

- 哪些水果更适合当前目标
- 水果应该如何与早餐搭配
- 大致应该吃多少
- 什么时间吃更合适
- 为什么这样建议
- 没有推荐水果时，应该用什么替代

## 6. MVP 核心场景

### 6.1 主场景

用户昨晚饮食较油腻，今天早上希望吃得清淡、舒服一些，于是向 RipePick 提问：

> 昨晚吃得比较油腻，今天早上我吃什么比较好？

### 6.2 期望结果

RipePick 返回一份以水果为核心的早餐建议，包括：

- 推荐水果
- 早餐搭配
- 简明推荐理由
- 建议份量或适量提示
- 可替代方案
- 必要的注意事项

### 6.3 可扩展场景

主场景验证后，可以扩展到：

- 想吃得清淡一些
- 想准备一份水果早餐
- 想吃当季水果
- 想补充某类营养
- 想比较两种水果
- 想了解某种水果的挑选和保存方式

## 7. 核心价值假设

如果 RipePick 能根据用户当前的饮食状态和目标，提供清晰、具体、容易执行的水果与早餐搭配建议，用户就能更有信心地完成当天的饮食选择，并逐渐提升健康饮食管理能力。

MVP 需要验证的不是“用户是否喜欢水果知识”，而是：

> 用户是否愿意在真实饮食决策场景中使用 RipePick，并认为它提供的建议比自己随意搜索更有帮助。

## 8. MVP 功能范围

### 8.1 P0 功能

1. **自然语言输入**
   - 用户可以用一句话描述当前饮食状态和目标。
   - 例如：昨晚吃得比较油腻，今天早上吃什么比较好？

2. **场景理解**
   - 识别用户的时间、饮食状态和期望目标。
   - 信息不足时，只追问影响推荐结果的必要问题。

3. **水果推荐**
   - 推荐一种或少量几种适合当前场景的水果。
   - 推荐应基于结构化水果数据和明确规则。

4. **早餐搭配建议**
   - 推荐水果与基础早餐食物的搭配。
   - 重点是帮助用户完成一顿早餐，而不是只推荐水果。

5. **解释与注意事项**
   - 解释推荐与用户目标之间的关系。
   - 提供适量、过敏、饮食限制等必要提示。
   - 不进行疾病诊断，不承诺解油腻、排毒或治疗效果。

6. **基础水果数据**
   - 水果名称
   - 季节信息
   - 基础营养信息
   - 口味和食用特征
   - 常见挑选与保存建议

7. **基础降级能力**
   - AI 服务不可用时返回明确错误。
   - 没有匹配结果时说明原因，并提供普通替代建议。
   - 数据不足时明确告知不确定性，不得编造事实。

### 8.2 P1/P2 功能，暂不纳入 MVP

- 用户注册、登录和长期健康档案
- 个性化偏好记忆
- 精确的地区和气候模型
- 社区投稿和用户评价
- 价格追踪和电商跳转
- 完整的蔬菜、肉类和全膳食规划
- 医疗级营养方案
- 长期健康趋势分析

## 9. 核心用户流程

```text
打开 RipePick
  -> 输入当前饮食场景
  -> 系统识别时间、状态和目标
  -> 必要时询问一个补充问题
  -> 推荐水果和早餐搭配
  -> 展示理由、适量提示和替代方案
  -> 用户继续追问或调整条件
```

## 10. MVP 输出原则

### 10.1 可执行

用户看完后应该知道下一步吃什么、如何搭配，而不是只得到一段百科介绍。

### 10.2 有依据

营养、季节和水果属性应来自结构化数据或明确来源。模型负责理解和组织语言，不应自由生成事实。

### 10.3 有边界

RipePick 提供一般性健康饮食信息，不替代医生、营养师或个体化医疗建议。

### 10.4 简洁优先

一次回答先给出一个主方案和一个替代方案，避免把用户淹没在过多选项中。

## 11. MVP 成功标准

### 11.1 用户价值指标

- 用户能够在一次交互后获得一份清晰的水果早餐方案。
- 用户能够理解推荐理由，而不是只看到结论。
- 用户能够继续调整条件并获得新的建议。
- 用户认为建议具有实际帮助，而不是普通搜索结果的重复。

### 11.2 产品质量指标

- 预先准备的核心场景测试中，大多数请求能够被正确理解。
- 推荐结果能够引用已有水果数据。
- 数据库没有相关信息时，系统能够明确说明，而不是编造。
- AI 服务失败、无结果和输入不清晰时，都有可理解的反馈。

### 11.3 初始验证方式

使用一组固定测试问题进行人工评估，至少覆盖：

- 早餐搭配
- 清淡饮食目标
- 当季水果
- 营养目标
- 两种水果比较
- 信息不足
- 数据库无结果
- 与水果无关的问题

## 12. 非功能要求

- 首屏和基础交互应保持快速响应。
- AI 回复需要支持明显的加载状态；流式输出属于体验增强项。
- 重要推荐结果应保留可追溯的数据依据。
- 用户输入可能包含健康信息，应尽量减少收集，并避免不必要的长期保存。
- 前后端接口、错误结构和数据字段需要稳定，便于后续替换模型或扩展推荐规则。

## 13. 主要风险

| 风险 | 影响 | MVP 应对方式 |
|---|---|---|
| 健康建议表述不严谨 | 用户误解或产生信任问题 | 使用一般性建议，避免医疗承诺 |
| AI 编造水果信息 | 直接损害产品可信度 | 基于结构化数据回答，增加固定评测集 |
| 范围过大 | 无法完成核心闭环 | 先聚焦水果与早餐场景 |
| 推荐过于泛化 | 用户感受不到价值 | 要求建议包含具体水果、搭配和理由 |
| 用户输入信息不足 | 推荐不准确 | 只追问真正影响结果的关键信息 |
| 数据来源不清晰 | 无法验证建议 | 为水果数据记录来源和更新时间 |

## 14. MVP 完成定义

当用户可以完成以下闭环时，MVP 达到第一阶段完成条件：

```text
用户描述一个真实饮食场景
  -> 系统正确理解
  -> 系统从已有水果数据中选择方案
  -> 返回水果与早餐搭配
  -> 解释理由并给出必要提示
  -> 用户可以继续追问或调整条件
```

此时不要求支持所有地区、所有食材、所有健康目标，也不要求建立完整的个人健康管理系统。

## 15. 待确认问题

以下问题不阻塞 MVP Brief，但需要在交互和技术设计阶段确认：

1. MVP 首先面向中文 Web App，还是同时面向移动端 Web 体验？
2. 用户是否可以匿名使用？
3. 哪些信息必须实时获取，哪些信息可以使用静态种子数据？
4. 首批水果数据采用哪些来源，如何记录可信度和更新时间？
5. 推荐结果是否需要展示数据来源？
6. 首个 AI 模型服务如何选择，成本、延迟和数据隐私的优先级是什么？

## 16. 下一阶段

MVP Brief 确认后，进入以下工作：

1. 设计主场景的用户流程和对话流程
2. 确定首页和推荐结果页面结构
3. 定义水果数据字段和首批种子数据
4. 定义前后端 API 契约
5. 实现第一条垂直链路
