# RipePick 后端 API 指南

这份指南帮助开发者快速理解后端 API 的用途、调用方式和维护约定。完整、可供工具解析的接口契约见 [`openapi.yaml`](openapi.yaml)。

## 当前状态

`POST /api/v1/recommendations` 是 MVP 推荐流程的目标接口，当前契约标记为 `planned`。请以实际后端路由为准判断接口是否已经实现；OpenAPI 描述的是约定，不代表服务已经具备该能力。

## 核心推荐流程

客户端首次提交用户当前的饮食场景或目标时省略 `session_id`。服务返回新建的会话标识；之后的每一轮（包括回答澄清问题）都携带该 `session_id`，并把本轮用户输入放在 `message` 中。澄清选项的 `value` 可以直接作为下一轮的 `message`。这样服务能在当前会话内延续必要上下文，不需要账号或长期健康档案。

服务会返回以下业务结果之一：

| `data.status` | 含义 | 客户端处理方式 |
| --- | --- | --- |
| `recommended` | 有结构化资料支持推荐 | 展示水果、早餐搭配、理由、份量提示、替代方案、注意事项和依据 |
| `clarification_required` | 缺少会影响推荐的关键信息 | 展示一个澄清问题及可选答案，收集补充信息后继续 |
| `no_match` | 当前资料或条件无法支持推荐 | 说明原因并展示可行的调整建议 |

AI 或推荐服务暂不可用时，使用 HTTP `503`。它与 HTTP `200` 下的 `no_match` 不同：前者表示服务暂时无法处理请求，后者表示请求已处理但资料无法支持结果。未知或过期的 `session_id` 返回 HTTP `404`，客户端应提示用户重新开始。

## 请求示例

```http
POST /api/v1/recommendations HTTP/1.1
Content-Type: application/json

{
  "message": "昨晚吃得比较油腻，今天早上吃什么比较好？"
}
```

续接示例：

```json
{
  "session_id": "5f36d50c-c392-43ec-9a02-79b58ad84173",
  "message": "no"
}
```

成功响应使用统一信封：`code`、`message`、`data` 和 `request_id`。每种业务结果的 `data` 都包含服务签发的 `session_id`。客户端应先检查 HTTP 状态码，再根据 `data.status` 选择业务界面。错误响应也包含 `request_id`，便于用户反馈问题时与服务日志关联；不要向用户展示内部堆栈或敏感诊断信息。

会话标识是临时上下文句柄，不是用户 ID 或健康档案 ID。客户端应将其视为敏感数据，不写入分析事件或普通日志。当前 API 尚未确定会话保留时长；部署前必须明确并披露保留/过期策略。会话过期后，客户端从新请求开始，不应自行重放可能已包含健康信息的完整历史。

完整字段、约束、示例和状态码见 OpenAPI 契约，不要在本指南重复维护字段定义。

## 产品与事实边界

- 推荐服务提供一般性健康饮食信息，不作疾病诊断、治疗或医疗级饮食处方。
- 水果属性、搭配、营养和注意事项应来自结构化应用数据或明确来源。模型可以理解表达和组织语言，不能代替事实来源。
- 没有足够依据时应返回澄清或无匹配结果，不得补造事实。
- MVP 先验证“描述场景 → 获得水果与早餐建议 → 理解推荐理由”的闭环，不默认扩展到账户、长期健康档案或完整膳食规划。

## 接口文档维护

`openapi.yaml` 是 HTTP 契约的唯一字段级来源。修改接口时：

1. 根据当前 MVP 和相关原型确认用户流程及状态，再修改 OpenAPI 契约。
2. 同一变更中更新服务实现和客户端使用方式；不要让实现悄悄偏离契约。
3. 只有当接口的用途、业务语义或维护流程变化时，才更新本指南；字段细节保留在 OpenAPI，避免重复。
4. 为新增或变更的接口保留请求、成功和错误示例，并说明哪些状态是业务结果、哪些是 HTTP/服务错误。
5. 在代码评审中同时检查契约与实现的一致性，以及无结果、澄清和服务不可用等降级行为。

MVP 推荐接口使用同步 JSON 完整响应。SSE 流式输出是后续体验增强，不属于当前推荐契约的实现前置条件。

版本化 API 路径（当前为 `/api/v1`）。对已发布客户端有破坏性的契约修改，应通过新版本路径迁移，不要直接改变既有字段语义。
